Submit results

A submission is a set of test cases. The maintainers approve each one by hand, which can take a few working days, then replay it on each program’s pinned build. {{submitting_md}} has the steps and commands.

  1. Run the tool. Choose any programs; each needs {{min_repeats_word}} runs, {{budget_hours_word}} hours by default. Keep every test case and its time. No fee.
  2. Convert and validate. An adapter turns each run into a bundle and python -m agent_software_testing validate checks it.
  3. Check for crashes. Run python -m agent_software_testing signatures on each bundle. If it reports any, restrict that program’s archive or leave out the crashing cases until the disclosure period is over.
  4. Deposit the bundles. Each goes to a permanent archive that issues a DOI, such as Zenodo, with its SHA-256.
  5. Open a pull request. It adds one file, submissions/<system_id>.json, to {{results_repo}}. The file names the tool, track, budget, model, bundle DOIs and hashes and gives your consent to publish under {{licence_data_text}}.

Propose a program

The {{program_form}} asks for the program and version, the source archive and its SHA-256, an OSI-approved licence, the input surfaces and a build recipe. {{proposing_md}} has the conditions.

Disclosure policy

Error kinds and counts of sanitiser findings are published for every program. Locations, stack traces and inputs of bugs not yet fixed upstream stay unpublished. Each count is of untriaged signatures.

A finding that looks like a real bug is reported to the project’s maintainers through its own reporting channel. Details may become public with the fix or {{disclosure_days}} days after that report and the maintainers may then credit the finders. Submitters do not publish details of an unfixed bug. Crashing inputs go in a restricted record or stay out. {{disclosure_md}} has the full policy.
