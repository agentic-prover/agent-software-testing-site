Contribute

For authors of a test generator who want it measured beside these tools without building baselines.

  1. Submit results
  2. Propose a program
  3. Report a problem
  4. Disclosure policy

Submit results

A submission is a set of test cases. The maintainers approve each one by hand, which can take a few working days, then replay it on each program’s pinned build. SUBMITTING.md has the steps and commands.

  1. Run the tool. Choose any programs; each needs three runs, six hours by default. Keep every test case and its time. No fee.
  2. Convert and validate. An adapter turns each run into a bundle and python -m agent_software_testing validate checks it.
  3. Check for crashes. Run python -m agent_software_testing signatures on each bundle. If it reports any, restrict that program’s archive or leave out the crashing cases until the disclosure period is over.
  4. Deposit the bundles. Each goes to a permanent archive that issues a DOI, such as Zenodo, with its SHA-256.
  5. Open a pull request. It adds one file, submissions/<system_id>.json, to agent-software-testing-results. The file names the tool, track, budget, model, bundle DOIs and hashes and gives your consent to publish under CC BY 4.0.

Propose a program

The program proposal form asks for the program and version, the source archive and its SHA-256, an OSI-approved licence, the input surfaces and a build recipe. PROPOSING-A-PROGRAM.md has the conditions.

Report a problem

Where to report a problem, by kind
What is wrongWhere to report it
The runner, validator, adapters or specificationThe bug form. Changes to the specification go through the specification change form.
A wrong or mislabelled numberThe data form. The correction goes into the next release.
A security problem in the runnerA private report, as SECURITY.md describes.
A bug in one of the 18 programsThe project’s maintainers through its own reporting channel, under the disclosure policy below.
The websiteThe website form.

Disclosure policy

Error kinds and counts of sanitiser findings are published for every program. Locations, stack traces and inputs of bugs not yet fixed upstream stay unpublished. Each count is of untriaged signatures.

A finding that looks like a real bug is reported to the project’s maintainers through its own reporting channel. Details may become public with the fix or 90 days after that report and the maintainers may then credit the finders. Submitters do not publish details of an unfixed bug. Crashing inputs go in a restricted record or stay out. DISCLOSURE.md has the full policy.
